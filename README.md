# Сбор корпоративных переписок в Telegram

Система автоматически сохраняет переписку в рабочих Telegram-чатах и позволяет
администраторам выгружать её за произвольный период. В чат добавляется
бот-коллектор, который пишет каждое сообщение в PostgreSQL и складывает
вложения на диск. Отдельный админский бот отдаёт эти данные: сообщения — JSON-файлом,
вложения — ZIP-архивом.

Зачем два бота: у них разные задачи и разные зоны доступа. Коллектор сидит в
групповых чатах и только пишет в базу, выгружать через него ничего нельзя.
Админский бот работает в личке, никогда не добавляется в рабочие чаты и отвечает
только пользователям из списка администраторов. Даже если токен коллектора
утечёт, выгрузить им архив переписки не получится.

## Что сохраняется

- текст сообщений и подписи к файлам;
- документы, фото, видео, гифки, голосовые, видеосообщения, аудио — файл скачивается
  в `storage/attachments/<telegram_chat_id>/`, в базе лежит относительный путь к нему;
- автор сообщения: Telegram ID, username, имя и фамилия;
- время отправки и время последней правки;
- ссылка на сообщение, которому отвечают, — иначе ветки обсуждения в выгрузке
  рассыпаются в плоский список;
- **история правок**: при редактировании прежний текст не затирается, а уходит
  в таблицу `message_versions`. При разборе спорных ситуаций обычно интересна
  как раз первая формулировка, а не итоговая;
- **происхождение пересылки**: у пересланного сообщения в авторах стоит тот, кто
  переслал, поэтому исходный источник сохраняется отдельно — человек, скрытый
  автор, чат или канал. Иначе чужие слова в выгрузке выглядят как слова
  пересылавшего;
- **служебные события** в таблице `chat_events`: кто вошёл и по чьей воле, кто
  вышел сам и кого исключили, смена названия и фото, закрепления, переезд группы
  в супергруппу. Для аудита состав участников и момент входа важны не меньше
  самой переписки.

Стикеры не сохраняются: содержания в них нет.

## Архитектура

Четыре независимых модуля, связанных только через общую базу данных. Ни один
не импортирует другой — коллектор ничего не знает о выгрузке, админский бот
ничего не знает о сборе.

| Модуль | Каталог | Задача |
| --- | --- | --- |
| Интеграция с БД | `app/db/` | Модели SQLAlchemy и CRUD-функции |
| Сбор данных | `app/collector/` | Слушает чаты, пишет сообщения и вложения |
| Администратор | `app/admin_bot/` | Диалоги выгрузки, проверка прав |
| Общий модуль | `app/main.py` | Запускает коллектор и админского бота в одном процессе |

Общие мелочи вынесены отдельно, чтобы модули не тянули друг друга: пути к каталогам
проекта — в `app/paths.py`, общие шаги диалогов админского бота — в
`app/admin_bot/handlers/common.py`.

## Стек

aiogram 3 (Telegram Bot API), SQLAlchemy 2, PostgreSQL, python-dotenv.
Разрабатывалось на Python 3.14, минимальная версия для aiogram 3 — 3.9.

## Установка

```bash
git clone https://github.com/Saichiro21/Work.git
cd Work

python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Создайте базу данных в PostgreSQL:

```bash
createdb -U postgres work
```

Таблицы создавать вручную не нужно — `app/main.py` вызывает `init_tables()` при запуске.

Учтите, что `init_tables()` добавляет только отсутствующие таблицы: новые колонки
в уже существующие он не дописывает. Если база создана более ранней версией
проекта, колонки в `messages` нужно добавить один раз вручную:

```bash
psql -U postgres -d work <<'SQL'
ALTER TABLE messages ADD COLUMN IF NOT EXISTS reply_to_message_id BIGINT;
ALTER TABLE messages ADD COLUMN IF NOT EXISTS forward_origin_type VARCHAR;
ALTER TABLE messages ADD COLUMN IF NOT EXISTS forward_from_name VARCHAR;
ALTER TABLE messages ADD COLUMN IF NOT EXISTS forward_from_id BIGINT;
ALTER TABLE messages ADD COLUMN IF NOT EXISTS forward_origin_date TIMESTAMP;
ALTER TABLE messages ADD COLUMN IF NOT EXISTS is_automatic_forward BOOLEAN NOT NULL DEFAULT FALSE;
SQL
```

Таблицы `message_versions` и `chat_events` создадутся сами при запуске.

## Переменные окружения

Все секреты читаются из `.env` через `load_dotenv()`. Скопируйте шаблон и заполните:

```bash
cp .env.example .env
```

| Переменная | Обязательна | Описание |
| --- | --- | --- |
| `DB_HOST` | да | Хост PostgreSQL, обычно `localhost` |
| `DB_PORT` | да | Порт, по умолчанию `5432` |
| `DB_NAME` | да | Имя базы данных |
| `DB_USER` | да | Пользователь PostgreSQL |
| `DB_PASSWORD` | да | Пароль пользователя |
| `COLLECTOR_BOT_TOKEN` | да | Токен бота-коллектора от @BotFather |
| `ADMIN_BOT_TOKEN` | да | Токен админского бота, отдельный от коллектора |
| `ADMIN_IDS` | да | Telegram ID администраторов через запятую |
| `COLLECTOR_CHAT_IDS` | нет | Белый список чатов: `telegram_chat_id` через запятую. Если пусто, коллектор пишет сообщения из всех групп, куда его добавили |
| `DISPLAY_TIMEZONE` | нет | Часовой пояс для показа времени в выгрузках, например `Europe/Moscow` или `Asia/Shanghai`. По умолчанию `Europe/Moscow` |

`ADMIN_IDS` при каждом запуске синхронизируются в таблицу `admins`, так что
достаточно дописать ID в `.env` и перезапустить процесс. Свой ID можно узнать
у @userinfobot.

Файл `.env` в `.gitignore` и в репозиторий попасть не должен.

## Настройка ботов

**Бот-коллектор.** Создайте бота у @BotFather, затем обязательно отключите privacy mode:
`/mybots` → выберите бота → `Bot Settings` → `Group Privacy` → `Turn off`. Без этого
Telegram будет присылать боту только сообщения, где его упомянули, и сбор работать
не будет. После этого добавьте бота в рабочий чат.

**Админский бот.** Создайте второго бота, его токен положите в `ADMIN_BOT_TOKEN`.
В группы его добавлять не нужно, он работает только в личных сообщениях.

**Как узнать `telegram_chat_id` чата.** Оставьте `COLLECTOR_CHAT_IDS` пустым,
запустите проект и напишите в чат любое сообщение. После этого ID можно взять
у админского бота: `/export` → «Показать список чатов» → «Показать ID чатов»,
номера там оформлены для копирования одним нажатием. Тот же список есть в базе:

```bash
psql -U postgres -d work -c "SELECT telegram_chat_id, title FROM chats;"
```

Нужный ID можно затем вписать в `COLLECTOR_CHAT_IDS`, чтобы бот игнорировал
остальные чаты. У обычных групп ID отрицательный, у супергрупп начинается с `-100`.

Если обычная группа превращается в супергруппу, её `telegram_chat_id` меняется,
и старый номер в `COLLECTOR_CHAT_IDS` перестаёт совпадать — сбор по такому чату
прекратился бы молча. Коллектор ловит этот момент, пишет новый ID в лог
предупреждением и сохраняет событие в `chat_events`.

## Запуск

```bash
python -m app.main
```

Поднимаются обе задачи сразу, через `asyncio.gather`. Если одна падает, вторая
корректно останавливается, а не остаётся висеть в процессе. Остановка — `Ctrl+C`.

Модули можно запускать и по отдельности, это удобно при отладке:

```bash
python -m app.collector.runner
python -m app.admin_bot.bot
```

### Автозапуск через systemd

Запуск из терминала живёт ровно до закрытия окна, поэтому для постоянной работы
в репозитории лежит готовая служба `deploy/telegram-archive.service`. Пути в ней
указаны для `/home/sai/projects/work` — поправьте под себя.

```bash
mkdir -p ~/.config/systemd/user
cp deploy/telegram-archive.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now telegram-archive
```

Служба поднимается заново после любого падения — сеть и Telegram отваливаются
регулярно, это нормальный режим работы. Состояние и логи:

```bash
systemctl --user status telegram-archive
journalctl --user -u telegram-archive -f
```

Осталась одна команда, которую нужно выполнить от root: без неё пользовательские
службы останавливаются, когда закрыт последний терминал.

```bash
sudo loginctl enable-linger $USER
```

В WSL нужен ещё включённый systemd — в `/etc/wsl.conf` должно быть:

```ini
[boot]
systemd=true
```

После правки `wsl.conf` выполните в PowerShell `wsl --shutdown` и откройте
терминал заново. PostgreSQL при этом должен запускаться сам
(`sudo systemctl enable postgresql`), иначе бот будет перезапускаться по кругу,
пока база не поднимется.

## Как выгрузить данные

Напишите админскому боту в личку. Пользователям не из `ADMIN_IDS` бот не отвечает вообще.

- `/start` — список команд.
- `/export` — сообщения чата за период в виде JSON-файла.
- `/files` — вложения этих сообщений в виде ZIP-архива.
- `/search` — поиск по слову: кто и когда о нём писал.

`/export` и `/files` спрашивают одно и то же в два шага: сначала `telegram_chat_id`
чата, потом период в формате `14.09.2026 - 14.09.2026`. Последний день входит
в выборку целиком, до `23:59:59`. Регистр команд не важен, `/Export` сработает
так же, как `/export`.

Ввод проверяется по порядку: сначала формат, затем существование дат и то, что
период не целиком в будущем, и только потом выполняется запрос. Если за период
сообщений нет, бот так и отвечает, пустой файл не присылается.

Ошибку формата бот пишет над тем же вопросом и ждёт даты заново. Если период
разобран, но данных за него нет, вместо пустого файла приходит экран с выходами:
назвать другие даты, вернуться к выбору чата или в меню.

Пример диалога:

```
Вы:  /export
Бот: Из какого чата взять данные?
     [ Показать список чатов ][ Показать ID чатов ]
     [ Назад ]

Вы:  нажали «Показать список чатов»
Бот: Выберите чат из списка и укажите его telegram_chat_id.
     [ Назад ]
     [ Отдел разработки ]
     [ Продажи ]

Вы:  нажали «Отдел разработки»
Бот: За какой период? Введите даты в формате ДД.ММ.ГГГГ - ДД.ММ.ГГГГ
     [ К выбору чата ][ В главное меню ]

Вы:  01.09.2026 - 14.09.2026
Бот: [export_-1001234567890_01-09-2026_14-09-2026.json] Найдено сообщений: 137
     [ Главное меню ]
     [ Выбор чатов ][ Выбор даты ]
```

Пока вы нажимаете кнопки, диалог живёт в одном сообщении: бот правит его текст и
клавиатуру на месте, поэтому переписка не растёт, а прошлый шаг не остаётся
висеть рядом. Ваши сообщения и команды бот не удаляет — история запроса видна,
как в любой переписке.

Если вы отвечаете текстом, следующий вопрос приходит под вашим ответом: иначе он
оказался бы выше него. У прошлого окна при этом снимаются кнопки, чтобы вести
дальше могло только нижнее. Так же ведут себя «Главное меню», «Выбор чатов» и
«Выбор даты» под выгрузкой: нужное окно открывается ниже файла, а сам файл
остаётся на месте.

### Поиск по слову

`/search` отвечает на вопрос «обсуждали ли это вообще»: выбираете чат, присылаете
слово или фразу, и бот показывает совпадения прямо в переписке — дата, автор и
отрывок с выделенным словом. Ищет по всей истории чата сразу, без учёта регистра,
по подстроке: `отчёт` найдёт и `Отчёты`.

Совпадений в чате показывается не больше десяти, самых свежих: длинные простыни
всё равно не читают, да и лимит длины сообщения Telegram близко. Полный список
приходит файлом по кнопке «Выгрузить найденное в JSON» — формат тот же, что
у `/export`. Кнопка «Сузить по датам» добавляет к поиску период, «Искать за всё
время» его снимает. Чтобы поискать другое слово, достаточно прислать его — ни
команду, ни выбор чата повторять не нужно.

Шаг назад возвращает диалог ровно туда, откуда он ушёл. Если вы попали на шаг,
прислав текст, «К выбору чата» и «К вводу даты» уберут и окно, и сам присланный
`telegram_chat_id` или неудачные даты, а прошлое окно оживёт на своём месте.

Список команд бот держит один: по «Назад» с первого шага окно диалога и вызвавшая
его команда убираются, и на виду снова остаётся меню. Если же ниже меню уже есть
присланный текст или выгрузка, всё это история: её бот не трогает, а меню
открывает на месте закрытого окна, внизу переписки.

Выбранный чат после выгрузки сохраняется: следующий период можно назвать сразу,
не вызывая команду заново.

Чаты идут от самых свежих по дате последнего сообщения, кнопок выводится не
больше двадцати. Отправить `telegram_chat_id` текстом можно на любом шаге —
этот способ работает всегда.

Формат JSON. Сообщения и служебные события идут одной хронологией, как в самом
Telegram, и различаются полем `тип`:

```json
[
  {
    "тип": "служебное событие",
    "событие": "участника добавили",
    "дата": "14.09.2026 14:20:05",
    "кто": "Иван Петров (@ivan)",
    "с кем": "Мария Иванова (@maria)",
    "подробности": "нет",
    "закреплённое сообщение": "нет"
  },
  {
    "тип": "сообщение",
    "отправитель": "Иван Петров (@ivan)",
    "текст": "Отчёт за август",
    "дата отправки": "14.09.2026 14:47:49",
    "была ли отредактирована": "да",
    "ответ на": {
      "telegram_message_id": 10,
      "отправитель": "Мария Иванова (@maria)",
      "текст": "Пришли, пожалуйста, отчёт",
      "дата отправки": "14.09.2026 14:31:02"
    },
    "переслано из": {
      "тип источника": "канал",
      "источник": "РБК (Редакция)",
      "id источника": -1001234567890,
      "дата оригинала": "01.08.2026 12:00:00",
      "автопересылка из канала": "нет"
    },
    "история правок": [
      {
        "текст": "Отчёт за июль",
        "заменено": "14.09.2026 14:52:10"
      }
    ],
    "список вложений": [
      {
        "file_type": "document",
        "file_path": "storage/attachments/-1001234567890/5_отчёт.xlsx",
        "original_filename": "отчёт.xlsx"
      }
    ]
  }
]
```

Выгрузку читают люди, поэтому пустых мест и технических `null`, `true` и `false`
в ней нет: вместо них стоят слова — `не ответ на сообщение`, `не пересылалось`,
`правок не было`, `да` и `нет`.

У событий входа и выхода поля `кто` и `с кем` совпадают, когда человек
сделал это сам, и различаются, когда его добавили или исключили, — в формулировке
события это уже учтено. `подробности` хранят то, что зависит от события: новое
название чата, отрывок закреплённого текста, новый `telegram_chat_id` после
переезда в супергруппу.

### Время и часовые пояса

В базе время хранится в UTC — так его не ломает переход на летнее время и переезд
сервера. Пользователю оно показывается в поясе из `DISPLAY_TIMEZONE`, и в этом же
поясе понимаются границы запрошенного периода: `14.09.2026` — это сутки по местному
времени, а не по UTC. Поэтому сдвиг часового пояса не «съедает» сообщения на краях
периода.

Команда `/files` нужна тем, у кого нет доступа к серверу: она присылает сами файлы.
Внутри архива вложения разложены по папкам с датами, а файл `список_вложений.txt`
связывает каждый файл с автором и временем сообщения. Если архив не влезает в лимит
Telegram на отправку, он разрезается на части. Про файлы, которые отправить не удалось
(удалены с диска или слишком велики), бот пишет отдельным сообщением.

## Ограничения Bot API

Сбор идёт через обычного бота, а не через юзербот, — отсюда несколько ограничений,
о которых лучше знать заранее.

- **Нет истории.** Бот видит только сообщения, отправленные после его добавления в чат.
  Выгрузить переписку за период до этого момента невозможно.
- **Файлы до 20 МБ.** Больше Bot API боту не отдаёт. Такое вложение не скачивается,
  в лог пишется предупреждение, само сообщение при этом сохраняется.
- **Отправка до 50 МБ.** Поэтому `/files` и разрезает большие архивы на части.
- **Privacy mode должен быть отключён**, иначе бот не увидит сообщения в группе.
- **Удаление сообщений не отслеживается** — Telegram не присылает ботам такие апдейты.
  Удалённое в чате сообщение остаётся в базе и попадает в выгрузку как обычное,
  без пометки: отличить его от живого нельзя.

## Про реакции

Реакции не собираются. Модель `Reaction` и функции `create_reaction` / `delete_reaction`
в базе оставлены, так что вернуть сбор можно без миграций — через апдейт
`message_reaction`, но для него бота нужно делать администратором чата и явно
перечислять этот тип апдейтов в `allowed_updates`. Практической пользы для выгрузки
переписки в реакциях нет, поэтому сбор отключён осознанно.

## Безопасность

- `.env` и содержимое `storage/attachments/` исключены из репозитория.
- Админский бот не отвечает никому, кроме ID из таблицы `admins`.
- При сборке архива путь каждого вложения проверяется на выход за пределы
  `storage/attachments/`, чтобы битая запись в базе не превратилась в чтение
  произвольного файла с диска.
